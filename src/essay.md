date: 2026-08

Take an ordinary service. It accepts connections from the internet and terminates TLS, so it parses attacker-controlled bytes with a general-purpose library. It proves its own identity to peers, so it holds a long-lived private key. It runs business logic against a database, so it holds a database credential. Written the ordinary way, that is one process under one uid, and all three jobs share an address space. There is nothing irresponsible about it. An enormous amount of software is built exactly this way.

Now write the same service as four processes under four uids, talking over local sockets that authenticate their peer. `netd` terminates TLS and holds no long-lived secret. `authd` holds the host key and exposes one operation, sign a well-formed challenge, and never returns key material. `appd` holds the database credential and accepts only a defined message schema, from `netd` and nobody else. `logd` takes append-only writes. None of this is novel — OpenSSH has been built this way since 2002, and Provos, Friedl and Honeyman<a class="ref" href="#r-privsep">[privsep]</a> wrote up the reasoning the following year. Postfix, qmail, and every browser you have used are the same idea. It also costs more: four supervised processes instead of one, serialization on a path that used to be a function call, latency, new failure modes when a socket goes away, harder debugging, and a schema that now has to be maintained as a real interface because it has become a security boundary.

Now drop Heartbleed<a class="ref" href="#r-heartbleed">[heartbleed]</a> into both.

Heartbleed was a buffer over-read in the TLS heartbeat extension, returning up to sixty-four kilobytes of adjacent process heap per request, repeatable as often as the attacker likes and invisible in the logs. Not code execution — a read primitive, which is exactly why it is the useful example. What the attacker gets is precisely and only what happens to be in the address space.

In the monolith, the address space is everything. The host private key is on that heap, along with the database credential, the session state, and the decrypted traffic of every other user currently connected. Whether a given read returns the key is a matter of heap layout and patience, and in 2014 the answer turned out to be patience: Cloudflare put a server up as a challenge and researchers pulled the private key off it within a day. Recovery is not patching OpenSSL. It is rotating an identity, reissuing, notifying relying parties, and assuming the database was read.

In the separated design the same bug is in `netd`, whose heap holds TLS session state for the connections it is currently serving, and that is all it holds. The host key is in `authd`, under a different uid, in a different address space, and a read primitive cannot cross an address space. The database credential is in `appd`, likewise. What still leaks is the in-flight plaintext of the connections `netd` is handling, which is genuinely bad and which no amount of process separation fixes, because handling that plaintext is the job. The design did not make the bug harmless. It decided, before the bug existed, which secrets were allowed to be in the room when one arrived.

Change the hypothetical and give the attacker code execution instead. The monolith outcome is unchanged — they already had everything. In the separated design they can now speak the IPC protocol, driving `appd` through its schema and asking `authd` to sign well-formed challenges. Real capabilities, but bounded by an interface somebody designed rather than unbounded by an address space that happened to contain everything. Same architecture, two bug classes, two different residuals, and you can only see either one by reasoning about the shape.

Here is the part that has bothered me for years. Nothing we built to measure security can tell these two systems apart.

They link the same library, so the SBOM is identical. They are affected by the same disclosure, so the CVE is identical. The base score is computed on the vulnerable component rather than on your deployment, so that is identical too, and both land in the same remediation bucket under the same policy with the same deadline. The scanner output matches. The audit tests whether critical vulnerabilities were patched inside the window, and both pass or both fail together. The pentest is scoped to the exposed interface, which is the same interface. A procurement questionnaire sees the same technologies. Every instrument agrees the two systems are in the same condition, and one of them loses its identity key while the other does not.

Heartbleed makes this almost too neat. NVD scored it 5.0 Medium under CVSS v2, and it was later rescored 7.5 High under v3.1. The bug that forced a global certificate reissue was rated medium, and the rescoring fixed nothing, because both numbers describe the component rather than your deployment of it, and the whole question was what your deployment kept in that address space. CVSS does have a slot for the answer — the environmental metrics exist so a consumer can rescore against their own architecture, and almost nobody populates them. Not from laziness. Doing it correctly requires knowing what compromise of that component reaches in your system, which is expensive. The industry built the field and then discovered the input was the scarce thing.

The difference between those two services is not a control. It is the arrangement of the system around the controls. And the engineer who proposes the separated design is asking for budget to change a property that every instrument reports as unchanged, while the engineer who does not propose it is out of compliance with nothing.

## Controls are cached answers

I have been circling this for a couple of years without stating it directly.

In [The Status Quo Outlived Its Status](https://unmitigatedrisk.com/?p=1307) I wrote that process is memory without comprehension — every rule is a compressed lesson, the compression is lossy, and the organization keeps executing the answer long after everyone who understood the question has gone. In [Why Continuous Assurance Did Not Happen Until Now](https://rmhrisk.github.io/continuous-assurance/) I argued that thirty years of compliance software cut the administrative cost of assurance and never touched the cognitive cost, which is why the annual audit survived everything meant to replace it. In [Why FIPS 140 Means Running Old Code](https://unmitigatedrisk.com/?p=1293) I looked at what a certificate actually tells you about the code sitting in your rack.

Those are three instances of one thing. Security controls are cached answers to security-design questions, and we scaled security by distributing the answers and discarding the reasoning that produced them.

This is not a new observation about what security *is*. Saltzer and Schroeder were writing about least privilege, complete mediation, and unwanted access paths in 1975<a class="ref" href="#r-saltzer">[saltzer]</a>. NIST treats security as an emergent property of a system and systems security engineering as a subdiscipline of systems engineering, which is SP 800-160<a class="ref" href="#r-nist160">[nist160]</a> in one sentence. Nobody forgot security design. It never scaled, and what we built in its place has been standing in for it ever since.

The reason it never scaled is that the reasoning is expensive, and it is worth listing what the reasoning actually consists of. Understand what the system is for. Understand who and what holds authority. Identify the assumptions the design depends on. Work backward from the consequences nobody can accept. Trace what becomes reachable when an identity, a component, or a trust boundary fails. Notice when two individually reasonable decisions compose into a dangerous path. Compare alternative architectures. Then decide which risks to eliminate, contain, detect, recover from, accept, or transfer. That requires holding a whole system in one head, keeping it there while the system changes, and being in the room when the consequential decisions get made.

What is less obvious is why this particular work resisted the automation that arrived for everything around it, and the reason is not that nobody tried. Design reasoning is non-local: you cannot decide whether an authority relationship is acceptable by examining that relationship, because whether it matters depends on parts of the system you are not looking at. A scanner works when the property it hunts can be recognized inside a bounded window of the artifact, which is true of a great many defects and false of nearly every design question. It is also counterfactual — the question is never what the system did but what becomes possible if some component behaves differently, so no amount of observing a working system answers it, which is why monitoring never grew into design no matter how good it got. And it has no ground truth. A test passes or fails; a design is correct until an adversary demonstrates otherwise, and the absence of a demonstration is not evidence. There is nothing to regress against, so the write-it-and-run-it loop that made the rest of software tractable never closes. Add that whether a residual risk is acceptable depends on business intent, which appears in no artifact and changes without notice, and you have four properties that each defeat a technique that worked somewhere else.

The obvious objection is that human design review has never scaled and never will, which is right about the history and wrong about the cause. Nothing here claims that review scales. The claim is narrower: the reasoning underneath it is expensive rather than impossible, and its cost is what determines how much of it gets done. If that cost is a property of reasoning, it can move. If it is a property of the problem, it cannot. I think it is the first, and most of what follows is an argument for why.

So we rationed. The highest-risk systems got real attention and everything else got something cheaper, and the cheaper thing was always the same operation: expert threat reasoning compressed into portable substitutes — rules, patterns, requirements, controls, certifications, audit tests — that let thousands of people make mostly-good decisions without repeating decades of analysis. That is not the failure. It is how any expert discipline scales past its experts; building codes are compressed structural engineering and clinical guidelines are compressed medicine. The problem is that compression drops the same two things every time: the threat model that justified the rule, and the means of knowing when the rule has stopped applying.

@@FIG02@@

The compressions worked, and the argument depends on that. MFA ended an entire category of account compromise. Memory-safe languages retired classes of defect that consumed a generation of researchers. Hardware key storage genuinely prevents extraction. FIPS validation really does establish properties about a cryptographic boundary. A compression that produced nothing would have been abandoned decades ago. What went wrong is subtler and harder to fix: they were useful enough to become the thing we buy, measure, mandate, and eventually mistake for the property they were supporting.

Take *keys belong in HSMs*, a rule I have spent a lot of my career on both sides of. It carries none of the capital cost, none of the ceremony and custodian overhead, no latency figure for the signing path, no throughput ceiling, and no disaster-recovery story, which is usually the hardest part. It also drops the only question that matters, which is how many reachable extraction paths that boundary removes in *your* system. A key is either in one or it is not. There is one item that belongs on that list and never appears, because it runs the wrong way: a certificate attests a specific version in a specific configuration, so a fix to the validated module is either a revalidation measured in years or a patch shipped outside the boundary, which quietly ends the state the certificate describes. Choosing validated cryptography buys slower response to disclosed vulnerabilities in exactly the component you were being most careful about. I went through the public record on this — 415 modules<a class="ref" href="#r-corpus">[corpus]</a>, 324 with no recorded update after initial validation, and only 62 percent of the extractable Security Policies pinning a software or firmware version at all.

That is a real trade and often a good one. Getting key material out of the application's process is worth something, the separate administrative domain is worth something, and for some systems both are worth the patch latency several times over. It stops being a trade at the moment nobody makes it because everyone makes it, and then you are paying an unpriced cost against an unnamed threat. What that forecloses is the interesting answer. For a lot of services, a key held by a local key-management process, running under its own user context, exposing a narrow signing interface, with a policy on what it will agree to sign and monitoring on what it is asked to sign, removes more of the actually-reachable paths per dollar than a remote appliance does, and leaves a residual you can name out loud. That is a defensible engineering position, and it is close to unsayable in an institution that kept the rule and threw away the reasoning, because the rule has no grammar for *better against this threat model, at this cost*.

## What the other professions kept

Building codes, clinical guidelines, and checklists are all compressions, and none of them ate the profession that produced it. A code does not stamp drawings — a licensed engineer does, their name goes on the seal, and they carry personal liability for the building standing up. A guideline does not treat a patient; a physician departs from it when the patient in front of them is not the patient it was written for, documents why, and answers for the outcome. A checklist does not command an aircraft. In each case the artifact is scaffolding around a judgment that stayed attached to a person, and what kept it attached is that someone's name was on the result and the name was worth something. Deviation was permitted because someone was accountable for deviating well.

Security compressed and kept none of that, and it is worth noticing how carefully each of our instruments avoids the claim. A risk acceptance says an executive tolerated a specific risk, which is not an assertion that the design is sound. An audit opinion says controls operated, and the better auditors will tell you plainly that is not the same as the system being secure. A vendor warranty covers a product, not your deployment. A penetration test reports what was found in scope in the time available, which is a statement about the test.

Try the question in your own organization. Who is personally answerable for the claim that compromise of the workforce identity provider does not reach production signing authority? Not who gets blamed afterward — that is a different and much more crowded question. Who has put their name to it in advance.

In most places the honest answer is nobody, and that is not negligence, because there is no instrument for it. No license, no seal, no standard of care, no professional body that can end your ability to practice, and therefore no mechanism by which a considered deviation from the canonical control becomes a defensible professional act rather than an audit finding. That absence explains a lot of behavior that otherwise looks like institutional stupidity: in a profession with signatures, an engineer who chooses a cheaper design and documents why is doing their job, while in one without, the same person has simply failed to implement the recommended control, and the only safe move is the canonical one.

The obvious inference is that security should be licensed, and I do not think that follows. A standard of care needs a body of knowledge stable enough that a practitioner's obligations can be written down and adjudicated years later by someone who was not there. Structural engineering has that; whether we do is a genuine question, and the field has an unhappy record with credentials that certify vocabulary rather than the ability to reason about a system. Naming a missing instrument is not the same as prescribing that one. It does set up something I come back to at the end, though. If a field cannot produce signatures, the nearest available substitute is a price.

## The property lives outside the boundary

The loss shows up first as a boundary problem, and it shows up in the same shape in three unrelated places.

A FIPS 140-3 validation<a class="ref" href="#r-fips140">[fips140]</a> provides real assurance about a defined cryptographic module in an approved mode, and much less about the product functions, networking, update system, operating system, and administration outside that boundary. A product can correctly use a validated module while depending entirely on behavior nobody validated. That is not a defect in FIPS — there has to be a boundary or there is nothing to validate. The error is letting the assurance attached to the bounded thing stand in for assurance about the system around it, which is why the U-Boot forks in the corpus bother me considerably more than the algorithm claims do.

Isolation has the same shape, and I wrote the long version in Containing the Optimizer<a class="ref" href="#r-optimizer">[optimizer]</a>. Containers, VMs, confidential VMs, and dedicated security processors are four mechanisms built for four adversaries making four different promises, and calling all of them sandboxes makes them impossible to tell apart. The sharper point is what none of them addresses: a wall with no holes does no work, so every real deployment cuts holes — an egress path, a write channel, a tool API, somewhere to keep state, a credential — and every hole hands back a property the wall was providing. Moving from a container to a confidential VM builds a taller, thinner wall around exactly the same holes.

Layering has a version of this that is easy to miss, and I run into it constantly in environments that have decided to presume compromise. The standard answer is to authenticate independently at the network, again at the host, again at the application, so that failure of one does not hand over reachability. That is real design and the instinct is right. The question is whether those layers are independent, and the usual honest answer is that nobody has checked. Three authentication layers chaining to the same trust anchor are three walls on one hinge; they will be counted as three controls and they will fail together. There is a sharper version of the test that I have started asking directly — which of these layers still holds if the asymmetric primitive underneath it breaks? Some protect their data plane with symmetric keys and survive, some do not, and even the symmetric ones are only as independent as their key establishment, which in most deployments runs back through the same certificates as everything else. The diagram shows separation. The failure domain does not. This is answerable in about a day and no framework asks for it.

PKI is the same shape again, and it is the part I know best. Cryptography can establish that a key produced a signature. It cannot tell you who should have been able to cause that signature, why a relying party should accept the authority behind the key, or whether the governance that delegated that authority is still sound. The certificate path is one graph and the governance that makes it meaningful is another, and [nearly every interesting failure](https://unmitigatedrisk.com/?p=1314) in the history of the WebPKI lives in the gap between them.

@@FIG03@@

The pattern repeats because the mistake is structural. The cryptography can be correct and the authorization wrong. The identity can be strongly authenticated and wildly overprivileged. The code can have no known vulnerability and sit in a catastrophic position of trust. The HSM can perfectly prevent extraction while the attacker is fully authorized to ask it to sign the thing they need, which is close to what happened with Storm-0558, where the boundary was not the thing that failed — the operations around it were.

The pattern is not confined to engineering, which is the best evidence that it is structural. Government classification is a compressed risk judgment carried on a marking, and almost every individual decision to apply one is defensible; the composition is what failed. The 9/11 Commission<a class="ref" href="#r-c911">[c911]</a> found that security requirements were nurturing overclassification and excessive compartmentation between agencies, and it named the incentive that produced it — no punishment for failing to share, criminal and civil exposure for sharing wrongly. One side of the error is priced and the other is free. Notice also when the bill arrived. The cost of decades of overclassification did not present as a classification failure. It presented as an intelligence failure, years later, attributed to agencies that could not connect what they already separately held.

## The proxy is easier to buy than the property

Once judgment has been compressed into artifacts, the artifacts are what the market can transact. A scanner has a price, an owner, output, and a renewal date. An HSM has a SKU, an SBOM is a file, MFA has a deployment percentage, and a pentest has a scope and a report. Now try buying this: understand the system well enough to determine whether its authority relationships, trust boundaries, dependencies, and failure modes create unacceptable attack paths, then compare alternative architectures, and keep doing it as the system changes.

One vendor says *hardware-backed key storage, zero trust, AI-assisted code review, continuous scanning, MFA, immutable logging, FIPS-validated cryptography*. Another says *compromise of our workforce identity plane cannot reach production signing authority; administrative recovery is independently governed, and the signing interface cannot export key material*. The second statement carries far more information about the property anyone actually wants, and it is far harder to evaluate. Does the path really disappear? Is the recovery identity actually independent? Can another role recreate the relationship? Does disaster recovery quietly reconnect the two domains? To check the claim, the customer needs much of the expertise they were trying to buy. The first vendor has handed them recognizable nouns instead, each checkable without reconstructing the architecture.

@@FIG04@@

Nobody has to be dishonest for this market to form. When the quality a buyer wants is expensive to observe, observable proxies become the unit of trade. But there is a structural point underneath that is worth stating plainly: the intermediate machinery holds its position as the thing being purchased precisely because the alternative cannot be evaluated directly. If a buyer could cheaply verify whether an architecture produced the properties they needed, a great deal of what currently gets sold would be repriced as an input rather than an outcome. CISA's Secure by Design and Secure by Demand<a class="ref" href="#r-cisa">[cisa]</a> work tries to shift this by giving purchasers better questions, and the questions are better, but the information problem is untouched. The largest buyers are starting to say the same thing in public: in April 2025 JPMorgan Chase's CISO wrote an open letter to the bank's suppliers<a class="ref" href="#r-jpmc">[jpmc]</a> arguing that vendors ship features faster than they build security and that modern integration patterns have quietly dismantled the boundaries that used to contain a compromise, which is the buyer side of this argument stated by a buyer with unusual leverage — and it meets the same wall, because what it asks for is architectures whose properties a customer can rely on, which is exactly the claim the market cannot cheaply check.

There is a second problem and it is worse: good design produces remarkably little theater. If you remove the relationship that lets a compromised workforce identity reach production signing, no counter shows attacks stopped, no alert queue fills, no dashboard turns greener. The dangerous path simply no longer exists. Compare that with a product producing ten thousand findings a month, which is doing real work and can demonstrate it continuously. The architecture that made those ten thousand events less consequential produces nothing anyone can screenshot for the quarterly review.

## When the rule outlives the reason

The same information problem changes what engineers inside the organization are allowed to propose, and this is the failure mode I see most often.

A key gets stolen. We learn that software-only storage is vulnerable to whole classes of compromise. We build smartcards, secure elements, HSMs, remote KMS. The rule that survives is *keys belong in HSMs*, when the original argument was *against these adversaries, for a key with these consequences, this boundary removes important extraction paths at a cost justified by the risk*. Now suppose the key belongs to a small service and a remote HSM is expensive, operationally heavy, or latency-sensitive enough that the team will not deploy it. The security model has two states, HSM-backed and not, the team cannot afford the first, and so the key lives in an environment variable.

There was an intermediate design available. Run the signing key in a separate process under a different user on the same host and give the application access only to a narrow signing interface. Is that an HSM? Obviously not — root still wins, a compromised kernel still wins, and depending on the interface, application compromise may still permit unauthorized signing. But code execution as the application user no longer discloses the key, dumping the environment no longer discloses it, accidental logging no longer discloses it, the interface can constrain operations, and key access becomes separately auditable. Several attack paths vanish for almost no money, and every one of those residuals can be stated and evaluated.

If the institution gives that design no credit because it is not the canonical control, building it becomes irrational. The practical choice collapses to *implement the approved control* or *take the finding*, and the middle of the curve disappears. That is the control cliff: risk reduction is continuous and institutional credit is a step function. Design asks which threats a mitigation addresses, which remain, what it costs, and whether the trade is right here; dogma asks whether the implementation conforms to the approved pattern.

@@FIG05@@

Retiring a rule takes decades. Shoe removal became universal in 2006, five years after Richard Reid, and ended in July 2025<a class="ref" href="#r-tsa">[tsa]</a> because scanning equipment had improved, not because anyone reopened the question. The tell is that PreCheck members were exempt throughout, so a traveler who paid a fee stood outside the control for its entire life. The rule was defensible in 2002, when the scanners genuinely could not see what Reid carried. It then ran for nineteen years without the reasoning that justified it.

The cliff has a mirror, and the mirror is worse because it looks like success. Encryption at rest is the cleanest example in wide deployment: the control is real, usually implemented correctly, and its threat model is physical — a stolen drive, a decommissioned array, a backup tape leaving the building in a van. Against those it works exactly as designed. Now name the thing that actually takes the data. An over-privileged service account, an injection flaw, a compromised application host, a support tool with a standing query path. In every one of those the database is asked politely for plaintext by something holding valid credentials and it complies, because complying is its entire job. At-rest encryption is not defeated in those scenarios; it is not present in them. And it satisfies everything — the questionnaire asks whether data is encrypted at rest, the auditor tests whether the feature is enabled, the framework awards the control, and nobody in the chain has said anything false.

The two failures are symmetric, which is how you know they share a cause. One withholds credit from a design that removes real paths. The other grants full credit to a control that removes none of the paths that matter. Both are what happens after the threat model has been stripped off, because the threat model is the only thing that would have told you which case you were standing in.

There is a related point about the HSM specifically that I want to make explicit, because it is the one people miss. The key matters because some other system accepts operations performed with it; the asset is usually not the key material but the authority it represents. Put the key in the finest HSM money can buy and then expose `sign(anything)` to a compromised caller, and the key is perfectly non-extractable while the authority is completely unprotected. What the device buys you is removal of key material from the application's process and a separate administrative domain around its use, and neither of those is what the certificate speaks to. The real questions are larger than storage: who can request an operation, what can they request, what happens when the caller is compromised, how durable is the resulting authority, and which downstream systems accept it.

## Why the artifacts keep multiplying

The third failure mode is that compression begets compression.

For decades vendors effectively said *trust us*. Customers stopped accepting that and asked what is in it, and the SBOM is a genuinely good answer to that question — when a catastrophic vulnerability lands in a widely deployed library, knowing which products contain it turns a scavenger hunt into a query. But presence is not what the operator wants to know. They want to know whether this vulnerability can hurt them in this deployment, which requires knowing whether the code was compiled, whether the feature is enabled, whether the function is reachable, whether attacker-controlled input reaches it, what privilege the process holds, what isolation surrounds it, and what the resulting capability actually gets you.

The SBOM does not answer that and was never supposed to. But institutions convert the thing they can require into the thing they wanted to know. Does the vulnerability affect this product? Add VEX. How do you substantiate VEX? Add reachability analysis. Under which configuration? Add configuration evidence. How do you know production still matches? Add attestation. Can an attacker change it? Add authorization data. Who can become that administrator? Add identity relationships. What if the IdP is compromised? Add upstream trust relationships. Is any of it still true today? Add continuous reconciliation. None of those additions is silly and almost all of them are useful, which is precisely why the process can continue indefinitely. Serialization moved pieces of the knowledge around; it did not abolish the judgment that joins the pieces together.

@@FIG06@@

The regress sustains itself for a reason that has nothing to do with anyone's intentions: every new proxy is easier to institutionalize than the judgment it stands in for. A proxy can have an owner, a budget, a tool, a maturity model, a reporting cadence, and an executive sponsor. Judgment can have a person. So the proxy wins the allocation fight every time and keeps winning it long after its next increment produces less risk reduction than changing the design would. That is not waste in the accounting sense, since each program delivers something. It is opportunity cost, and it compounds.

Follow it far enough and you get a strange but entirely plausible result. Every product has a current SBOM, every vulnerability has a VEX statement, every configuration is attested, every identity relationship is inventoried, every control emits evidence, every dashboard is green — and a three-step route still exists from an internet-facing service to the authority that can end the company. Nobody in that chain has necessarily done anything wrong. We have documented the insecure system extremely well.

## The attacker never agreed to our abstraction

None of the compression is visible to the attacker, and this is where the mismatch stops being philosophical.

I wrote the general version of this in [The Status Quo Outlived Its Status](https://unmitigatedrisk.com/?p=1307). Conway observed in 1968<a class="ref" href="#r-conway">[conway]</a> that any organization designing a system is constrained to produce a design that copies its own communication structure, and security has a sharper version, because defenses are not built by whoever designed the system — they are built by whoever was funded to build them. The system mirrors the organization that produced it, the defenses mirror the organization that paid for them, and nothing requires those two to agree with each other or with anything an attacker cares about.

Look at how the money divides. Endpoint, identity, AppSec, cloud, network, SOC, vulnerability management, GRC. That is not a taxonomy of risk, it is a set of reporting lines. The defender's allocation problem is to cover every domain adequately, because an uncovered domain is an unbounded liability and each domain has an owner who must answer for it, so spend is spread by structure and each team produces real coverage of the surface it was handed. Where organizational boundaries coincide with trust boundaries the defense is good. Where they diverge, nothing is watching, because a path crossing four teams is on none of the four backlogs. The attacker has a different cost function entirely: they allocate nearly everything to identifying and exercising the single cheapest viable route and abandon the rest, and they do not have to be adequate anywhere except along one path.
That asymmetry is why something like

> internet-facing service → application identity → CI system → deployment credential → production administration → signing service

survives so much spending. The application is supposed to have its identity. The identity may legitimately reach CI. CI may legitimately hold deployment authority. Operations may legitimately administer production. Production may legitimately invoke signing. Six teams can examine their own edge and find nothing absurd. The attacker only needs the composition, and no team owns it.

@@FIG08@@

Kill the obvious fix before anyone reaches for it. The inverse Conway maneuver says reshape the organization until it produces the architecture you want, and in product engineering that often works. It cannot work here. No org chart is isomorphic to an attack graph — the graph is denser than any reporting structure, it runs through vendors, SaaS systems, recovery paths, temporary privileges, customers, and support tools you do not employ, and it changes every time somebody grants a permission on a Tuesday afternoon. The compositions outnumber the teams, so either the consequential paths keep going unowned or something other than a team has to hold them.

This is why BloodHound<a class="ref" href="#r-bloodhound">[bloodhound]</a> mattered. Individual directory permissions were not secret before BloodHound; what changed was the representation. Put identities, privileges, groups, sessions, and administrative relationships into a graph and ask what they compose into, and the interesting unit stops being the permission and becomes reachability. Not *is this permission appropriate* but *what becomes possible because this permission exists alongside the rest*, which is much closer to the attacker's question than to ours.

## Cheap reasoning makes the mismatch worse first

The structural problem came first, and what AI changes is its price, so it is worth being careful about which side of the ledger moves.

Consider what an attacker does looking for a path. Gather information, form a hypothesis, follow an edge, find it blocked, back up, try another, combine two facts nobody had considered together, rank several routes by cost and consequence. Almost all of that is reasoning over a representation. Now consider what the defender does after discovering a dangerous architectural relationship: change an API, migrate customers, rewrite authorization, reissue credentials, alter disaster recovery, accept latency, retrain operators, coordinate four teams, and support the old architecture for another year. Almost none of that is reasoning. Machine reasoning therefore reduces the attacker's cost faster than it reduces the defender's cost of changing the system, and this holds even if model capability stopped improving today.

@@FIG09@@

Post-quantum migration shows the distinction at the largest scale currently running. Google has been working on it for roughly a decade and targets 2029 for Google Cloud, with some hardware riding natural replacement cycles past that, while NIST IR 8547<a class="ref" href="#r-pqc">[pqc]</a> anticipates final deprecation of the quantum-vulnerable algorithms somewhere between 2030 and 2035. That is close to the best-resourced actor available, migrating a stack it controls end to end, on a fifteen-year clock, and the hard part was never discovering that the algorithms need replacing. It is inventory, dependency analysis, negotiation, standards, certification, and physical replacement. The assurance apparatus is part of that cost and nobody budgets it: as of mid-2026 essentially no FIPS certificates existed for the core post-quantum algorithms, validation runs two to three years end to end with the post-submission stage alone averaging 579 days, and regulated buyers cannot deploy what is not validated. The instrument built to give those buyers confidence is now among the things setting the pace of the migration it was supposed to make safe.

The offensive side gets a cleaner benefit, and there is at least one measurement pointing that way. Anthropic evaluated frontier models<a class="ref" href="#r-anthropic">[anthropic]</a> building working exploits directly from disclosed patches, producing eight code-execution exploits across eighteen Firefox patches and privilege escalation for eight of twenty-one Windows kernel vulnerabilities where no source was available. The count is not the interesting number. The first working Firefox exploit arrived in under an hour, and the release carrying the fix was still eighteen days away. Patch cadences were designed on the assumption that weaponizing a disclosed patch costs expert-weeks and that few people can do it, and an interval measured in tens of minutes against a release measured in weeks is a different regime.

That does not mean every attacker suddenly wins, or that defenders get nothing from the same models — they will use them for code review, investigation, configuration analysis, threat modeling, and evidence collection. The near-term asymmetry is simpler than that. Information can move at machine speed and organizations still change at organizational speed, and the industry we built already assumes that finding a dangerous condition and removing it happen on very different clocks.

## Nobody can price an architecture

Not every risk should be eliminated. SP 800-37<a class="ref" href="#r-nist37">[nist37]</a> recognizes acceptance, mitigation, avoidance, and transfer as legitimate responses, and if eliminating a class of loss requires a $20M redesign while an insurer will absorb much of it for a far smaller premium, buying the contract can be the correct engineering decision. Insurance is more interesting than another control, though, because insurers eventually have to price the result.

Today they observe the same proxies everyone else does: MFA, EDR, backups, vulnerability management, incident-response capability, historical claims.<a class="ref" href="#r-munichre">[munichre]</a> It is easy to picture the correction running its course — cheap adversarial search changes the real loss distribution, losses show up in claims, insurers reprice, and somewhere down that chain architecture acquires a number the CFO can read without becoming an architect. Every link in that chain is slow, but slowness is not the interesting part. The binding constraint is that the underwriter has exactly the same observation problem the buyer does.

They price MFA and EDR because MFA and EDR are observable. If an underwriter could cheaply verify *workforce identity has no path to signing authority*, they would already be pricing it — the incentive is enormous and free of the buyer's conflicts. They are not, because establishing that claim requires reasoning across identity, infrastructure, configuration, code, and operations at once, and that has always cost more than the answer was worth to any single party. So the loop cannot close on claims data alone: loss experience can say that something changed, but it cannot say which architectural feature to price, or verify it at underwriting time across a book of thousands. And as with classification, the harm arrives late and wearing someone else's name, which is exactly the condition under which a feedback loop teaches nothing.

@@FIG10@@

The constraint is not lack of interest in architectural security. Buyers, auditors, executives, and insurers all have reasons to want the answer. What none of them can afford is the reasoning required to produce it and keep it current. That reframes the question: not whether AI can do security architecture, but whether machine reasoning can make architectural claims cheap enough to *inspect*, because the moment they are inspectable there is already a party waiting to price them.

## The representation we never built

We already have several examples of what happens when the right representation makes an expensive reasoning problem cheap. Joern<a class="ref" href="#r-joern">[joern]</a> constructs Code Property Graphs so properties of large codebases can be explored through queries rather than reconstructed by hand, and CodeQL<a class="ref" href="#r-codeql">[codeql]</a> does something similar. BloodHound represents identity relationships. OpenTelemetry<a class="ref" href="#r-otel">[otel]</a> derives service graphs from observed traces. SBOMs give composition, IAM gives principals and permissions, configuration gives intended state. Each is incomplete for this problem and each demonstrates the same trick: a better representation converts reasoning that was artisanal into reasoning that is merely a query. None of them answers a security question; all of them changed what it costs to ask one.

The gap is that every one of them begins too late, because they start from something already built. Before the code there was a decision about what the system should permit. Before the IAM permission there was a decision that a principal should hold some authority. Before the private key there was a protocol that required persistent signing authority. Before the network connection there was a relationship the design intended to exist.

A representation that starts earlier needs six things, and since a wishlist is not a specification, they are worth being declarative about. The **property** somebody decided must remain true. The **principals and authority relationships** it depends on, which is the question of who can cause what. The **design decision** taken to make the property hold, with the alternatives considered and rejected. The **assumptions** that decision rests on, written down so they can be checked rather than silently inherited. The **residual risk** knowingly accepted, which is the part a rule never records because a rule has no way to say *and we decided this was fine*. And the **conditions under which the claim stops holding**, which is the piece compression always drops and the only one that lets the representation invalidate itself. Most design documents describe why a decision looked correct at the moment it was made and almost never state its invalidation conditions. That last element is what separates this from a wiki page.

It is a design tool, not a documentation tool. Take the property *compromise of the application must not disclose persistent signing authority* — no product is named in that sentence, and the candidates become comparable against it. The environment-variable design yields `app compromise → key disclosure → persistent signing authority`. A separately permissioned local signer removes direct key disclosure but leaves host compromise. Moving the signer to another host removes another path. A remote KMS or HSM removes more extraction paths while leaving a compromised authorized caller able to exercise signing. A protocol redesign that eliminates the long-lived key removes the question entirely. Each option carries a different cost and a different residual, and that is the reasoning the control cliff destroyed, made explicit enough to compare.

@@FIG11@@

Once a decision is represented that way, reality can disagree with it. Say the team takes the local signer because a remote KMS is not justified by the residual host-compromise risk. The design now carries three assertions: the application cannot read key material, the signing interface accepts only transaction-shaped payloads, and the signer identity cannot be assumed from the workforce identity plane. Each is falsifiable by evidence somebody is already collecting. The first meets code analysis, which finds a crash-dump endpoint that maps the signer's memory. The second meets a runtime trace showing the interface accepting an arbitrary byte string from an integration harness that shipped by accident. The third meets the IAM graph, which finds a break-glass role granting assume rights to on-call, and on-call is a workforce group. Three contradictions, and nobody had to imagine the attack in advance. The design said what had to remain true and the implementation disagreed in three places.

That gives a very different loop from a compliance checklist: desired property, threat model, design, implementation, observation, contradiction, redesign. It is also where design and continuous assurance finally connect. Design says what must remain true, assurance asks whether reality still supports the claim, and continuous assurance without continuous design is a faster way to prove the wrong architecture is behaving exactly as specified.

@@FIG12@@

The danger is obvious enough to name before anyone builds it. The instant this becomes *Design Graph Coverage: 94%*, with a standard, a procurement mandate, and an audit test for currency, we have invented the next SBOM. The defense is in what the representation is for — not *here is the graph, therefore we understand the system*, but *here is what we currently believe about the system, find the shortest path that proves us wrong*. A representation optimized to be attacked resists institutionalization in a way one optimized to be certified does not.

## The scarce resource moved

There is a change happening one layer down that makes this more urgent. Generating code got cheap very quickly, and an assistant can produce thousands of lines of plausible implementation in an afternoon, but net additions to shipped systems have not moved remotely as far — because the bottleneck was never typing. It was understanding the existing system, deciding what should change, reviewing the consequences, debugging, testing, integrating, operating, and coordinating with other people. Lines of code was always a bad productivity metric and that is now the useful part, because it counts almost exactly the thing that became cheap.

@@FIG13@@

Security has the same problem in a sharper form. Producing another finding is getting cheap, and so is another control test, another policy mapping, another piece of evidence. The scarce part is deciding what the system ought to permit and whether all the pieces together produce that result. It is worse than neutral for security, because a flawed architectural assumption used to propagate at the speed of a person implementing it and can now cross thousands of lines and many components before lunch, in a form that looks finished.

There is a ladder here worth walking, because the rungs are easy to conflate. *Sensitive keys should be protected from extraction* is retrieval. *This application keeps the key in an environment variable, therefore application compromise discloses persistent signing authority* is contextual analysis. *A local constrained signer removes the highest-probability extraction paths at substantially lower cost than a remote HSM, leaving host compromise as an accepted residual* is design tradeoff reasoning. *The system only needs this long-lived authority because of the protocol we chose, and changing the protocol makes several attack paths disappear together* is architecture. Everything below that last step makes the existing machine faster; only the last step changes what the machine is for.

That ladder sorts the work by its object; there is a second axis, the method, that matters as much. Early code generation was autocomplete over nearby context. Then came genuinely hard implementation reached by brute force — write it, compile, run, fail, mutate, repeat — which works and scales with how many loops you can afford. What has been shifting is the ratio, more of the answer coming from an internal model of the system and fewer loops spent discovering it by trial. That is the distinction that matters for architecture, because architecture is the one place brute force is unavailable: you cannot reach a trust-boundary decision by trying it in production and watching it fail, since the failure is the outcome you were trying to prevent. Design reasoning means holding a model and interrogating it, so a system that only arrives at good answers by iterating will never reach the top rung, while one whose competence comes from the model might.

@@FIG14@@

A model can emit all four sentences today, and that is not the bar. The bar is deriving them from the actual system, distinguishing evidence from assumption, noticing missing evidence, finding alternatives nobody proposed, and staying correct as the implementation changes. We are plainly not there — today's systems reason impressively over bounded technical problems, while maintaining a reliable model of a large, evolving organization and making good architectural tradeoffs inside it remains much harder. Threat modeling keeps evolving, including work like Adam Shostack's PHANTOM-B<a class="ref" href="#r-phantomb">[phantomb]</a> for LLM-specific threats, but eliciting possible threats is still different from maintaining an executable model of the properties an organization intended to preserve.

Whether that gap is a categorical limitation or the next point on the same curve, I do not know, and neither does anyone else. The reason to care is not that a machine would replace the architect. It is that the architect's reasoning would become something a buyer, an auditor, or an underwriter could inspect.

## What changes if it does

None of this makes controls obsolete, and nothing above should be read as an argument for buying fewer of them.

If machine reasoning never gets much past code and bounded technical analysis, we get a faster version of the industry we already have: more findings, more code, more evidence, more tests, more remediation assistance. Valuable, and not a change in kind. If it reaches architecture, today's artifacts move back into their proper position as premises. The SBOM becomes evidence about composition, the Code Property Graph evidence about implementation, the identity graph evidence about authority, runtime traces evidence about interaction, threat intelligence evidence about changing attacker capability. None of them has to pretend to be security, which makes today's pipelines more valuable rather than less.

Then the questions change. Instead of *do we have an HSM*, which extraction and signing-abuse paths remain. Instead of *do we have an SBOM*, which component failures create consequential reachable paths in this deployment. Instead of *is MFA deployed*, what authority stays reachable after compromise of a factor, a session, a device, a recovery process, or the identity provider itself. Instead of *is this system compliant*, which claims about its security properties can the available evidence falsify.

And then the money moves. The existing market earns most of its revenue applying controls to systems that have already been designed, which is the only available response when redesign costs more than monitoring. Change that ratio and some portion of the spend migrates upstream, from buying another mechanism to watch a dangerous relationship to removing the relationship. That is not a smaller market. It is a different one, and the incumbent position in it is far less secure than the current one.

A design system worth having should argue back. Propose an HSM and it asks what happens when the authorized caller is compromised. Propose network isolation and it finds the management plane crossing the boundary. Propose MFA and it inspects recovery. Propose a process boundary and it shows what root still gets. Propose insurance and it separates transferable financial loss from operational, legal, and reputational consequence. Propose doing nothing and it tells you which fact would make that irrational. That does not replace human judgment; it concentrates it where it belongs — materiality, business intent, proportionality, novel threats, operational tradeoffs, acceptance of residual risk, accountability — and hands the machine the part machines may become extraordinarily good at, which is holding more relationships at once, searching more paths, and continuously trying to prove the current answer wrong.

We never stopped knowing how to do security design. We could not afford to apply the reasoning everywhere, so we compressed the results into standards, controls, patterns, certifications, checklists, findings, and artifacts. That was rational, and it let a small number of experts influence systems they could never personally review. The attacker never had to use the compression. They always got the real system — the identities, dependencies, trust relationships, configuration, recovery mechanisms, forgotten permissions, and ordinary decisions that compose into a path — and they searched it.

Cheap reasoning will make that asymmetry hurt before it helps, because searching a system gets cheaper before changing one does. But the rationing that produced all of this was never a law of computing. It was a price, and prices move.
